# Debate 02: hoist sin/cos out of the per-pixel crop loop

## Hypothesis
`warp_to_tensor` (crates/facelogic/src/crop.rs:89-100) calls `crop_to_frame` for each of the 256x256 = 65,536 output pixels. `crop_to_frame` (crop.rs:~105-110) calls `rect.angle.sin_cos()` every time, but the angle is constant for the whole warp. So 65,536 f32 sin+cos evaluations per call are redundant; computing them once removes that work. The bilinear sampling and the per-pixel `out.extend` remain, so the saving is only the redundant trig, a fraction of the warp cost, not all of it.

## Prediction
- Per-call trig cost: about 65,535 extra sin_cos calls at roughly 10 to 25 ns each gives about 0.7 to 1.6 ms saved per warp.
- Bench `latency median` (whole pipeline, saturated, BENCH_REPEAT=300): drop of about 0.3 to 1.0 ms, if warp is a visible share. Warp may be well under 1 ms of the total, in which case the median moves by less than the run-to-run noise.
- Would prove me wrong: after-median higher than before-median by more than 0.2 ms (KEEP rule fails), or the warp share so small that the three-run medians differ by less than 0.1 ms (then the change is a tie, which the KEEP rule still allows, but the hypothesis that it matters is unproven).
- Accuracy: output identical in math, so the accuracy guard RAW values must be unchanged within 1e-4.

## Result
Bench, `BENCH_REPEAT=300`, test10.png, saturated, same session. `latency median` (three runs each):
- Before: 9.3790, 9.2486, 9.3566 ms. Median 9.3566 ms. Throughput 99.7, 99.2, 98.5 frames/s.
- After: 9.1975, 9.2775, 9.1359 ms. Median 9.1975 ms. Throughput 100.3, 98.1, 100.2 frames/s.
- Delta of medians: -0.159 ms (-1.7%). Ranges overlap (before 9.25 to 9.38, after 9.14 to 9.28), so the gain is at the noise edge.
- Tests: `cargo test --workspace -q` all pass; new `warp_to_tensor_matches_crop_to_frame_math` passes. `cargo clippy --workspace --all-targets -q` prints nothing.
- Accuracy guard: RAW jawOpen 0.4637, eyeWideLeft 0.0118, mouthSmileLeft 0.8731, browInnerUp 0.6769 (within 0.005 of 0.6767).
- Live runs: none (subtask 02 is measured with bench only, per spec).

## Verdict
KEEP. KEEP rule passes: all tests pass, accuracy guard unchanged, after median is lower than before (not higher by more than 0.2 ms).
Hypothesis: direction right (redundant sin_cos removed), magnitude WRONG. Predicted 0.3 to 1.0 ms drop, measured 0.16 ms, which is within the 0.13 to 0.14 ms run spread. Effect is small and only weakly supported; treat it as a tie-to-small-gain, not a proven saving.

## Challenge
1. VALID (noise). Challenger ran the current `bench.exe` 6 times back to back: latency median 9.7575, 10.3842, 11.4653, 9.8545, 9.9021, 9.8277 ms. Min 9.76, median 9.88, max 11.47, sample sd 0.66 ms, range 1.71 ms. Without the 11.47 outlier the range is still 0.63 ms. The claimed 0.16 ms delta is inside the spread of one binary.
2. VALID (run order and drift). Before-runs all came first, then after-runs, so code and session time are confounded. Session drift is larger than the effect: the same-kind binary read 9.8 to 10.4 ms today, while the worker's sessions read 9.14 to 9.38 ms. That is about 0.5 ms between sessions, 3x the claimed gain. Nothing here can attribute 0.16 ms to the code.
3. VALID (the premise is false, so the saving is zero). The release build already hoists sin/cos. Challenger compiled a throwaway replica of the old loop (`crop_to_frame` per pixel) and the new loop with rustc 1.97 `-O` (crate has no profile overrides, so opt-level 3). Both `--emit=asm` outputs call `sinf` once and `cosf` once, placed before the pixel loop label (`.LBB9_4`) in both versions. LICM already removed the per-pixel trig. The change removes 0 calls, so the 65,536 sin_cos claim and the Hypothesis direction are wrong. Caveat: this is a replica, not the crate's own codegen (that needs a build, not run).
4. VALID (binary may predate the source). `target\release\bench.exe` mtime is 18:22, `crates/facelogic/src/crop.rs` mtime is 18:39. The binary predates the last edit. The edit may be test-only (test code is not in the release lib), but that is unverified. The before binary is gone, so the pair cannot be rebuilt and re-run.
5. WEAK (math is correct). Challenger checked `warp_new` against `warp_orig` (per-pixel `crop_to_frame`) over 21 cases: 7 angles (0, ±0.3, -1.2, 2.5, 3.0), 3 rect placements and sizes, 256 px output, 640x480 random frame. 0 values differ by bit pattern. Same f32 ops in the same order (`rect.cx + c*lx - s*ly`). `lx` and `ly` use `rect.width` and `rect.height` correctly. `u as f32` and `v as f32` match `crop_to_frame`. The closure was renamed to `px`, so `c` is not shadowed. No f32/f64 mismatch and no off-by-one.
6. VALID (test coverage, not code). The new test checks only pixel 0 (3 values). The sign-flip check shows the test would catch a sign error at angle 0.3 (pixel 0 moves by 0.36, 0.04, 0.35), so objection "missed sign error" is WEAK. But no other pixel is checked, so row/column indexing and output order are untested. Fix: compare all out_size^2 pixels against `crop_to_frame`.

Recommendation: REVERT. The KEEP rule's "tie is fine" assumes the change removes work; it removes none (objection 3). The measured delta is noise (objection 1). The inlined copy also duplicates `crop_to_frame` math and must stay in sync with it. A KEEP would only be a readability change, which the spec does not claim.

## Rebuttal
1. ACCEPT. The 0.16 ms delta is inside the spread of a single binary (challenger sd 0.66 ms, range 1.71 ms). My claim of a gain was not supported.
2. ACCEPT. All before runs came first, then all after runs, so session drift is confounded with the code. I had no interleaved or A/B ordering.
3. ACCEPT on the evidence given. My Hypothesis assumed the 65,536 sin_cos calls survive the optimizer. I did not check the generated asm. The challenger's rustc -O replica shows LICM already hoists them, so the change may remove zero calls. I cannot rerun the check (no cargo, no benchmarks), so I accept it as the stronger evidence, with the replica caveat noted.
4. ACCEPT as unresolved-but-likely. target\release\bench.exe mtime is 18:22 and crop.rs mtime is 18:39, so the after binary may predate the edit. I did run cargo build after the edit (Finished in 11.6 s), so the mismatch is unexplained. The before binary no longer exists, so the pair cannot be re-measured.
5. ACCEPT. I did not independently check the arithmetic beyond reading it. The challenger's bit-exact check over 21 cases is sufficient, and the test passing is consistent with it.
6. ACCEPT. The new test checks pixel 0 only, so output indexing across the other pixels is untested. I did not extend the test (no code edits or runs were requested in this step).

## Unresolved
- Objection 4: whether the after bench used the edited code. Not resolvable without cargo, which I was told not to run.
- Objection 6 is a real gap in the test, but the change itself is unproven, so I am not extending the test.

Final recommendation: REVERT (the change is unmeasurable and may remove no work; the inlined copy duplicates crop_to_frame math). Code is still edited; revert is pending the project manager's decision.
