# Debate 07: single-variable attribution of the window cost

## Hypothesis
The window costs about 75 CPU points and about 400 MB (subtask 01 facts). I think most of that is the avatar, not the preview and not the bare Bevy window.
- Avatar (VRM): `window.rs:431-434` spawns the VRM. `bevy_vrm1` loads the whole glTF: MToon materials, skinned meshes, spring bones, and decoded textures. Decoded texture and mesh data kept as CPU copies in `Assets<Image>` and `Assets<Mesh>` should be the main MB. Per-frame skinning and material updates should be the main CPU points.
- Preview: `window.rs:319-334` copies one 640x480 RGBA frame (1.2 MB) per camera frame into a `StandardMaterial` texture (`window.rs:435-459`). Subtask 06 measured the upload at about 0.1 ms per frame, so it should be small in CPU and about 2 to 5 MB in memory.
- Bare window: `DefaultPlugins` (wgpu, DXGI, swapchain, render graph) with a camera, a light and vsync at 60 fps. This is a fixed cost that should show as a sizeable CPU share and tens to low hundreds of MB.
- Cheaper explanation to watch for: the avatar may be cheap on CPU (GPU does the skinning) and expensive only in memory. Then variant C shows MB but not CPU.

## Prediction
Numbers for 15 s live runs, NO face, same kind as subtask 01 (CPU average, peak working set in MB).
- A (full): 85 to 93 CPU, 457 to 532 MB (matches subtask 01).
- B (no preview): A minus 0 to 3 CPU points and A minus 0 to 5 MB. Preview is inside noise.
- C (no VRM): A minus 35 to 50 CPU points, A minus 200 to 300 MB. Avatar is the main cost.
- D (no VRM, no preview): 25 to 40 CPU points, 120 to 200 MB. This is the bare window.
- Consistency: A minus C should be about 40 to 60 points and about the same as (C minus D) plus 0 to 5.
- What would prove me wrong: preview saves more than 5 CPU points or more than 10 MB (then the preview is a real cost), the avatar saves less than 25 points (then the bare window is the main cost), or D is above 50 points (then the bare Bevy loop, not the avatar, dominates).

## Result

Run-to-run spread is large: A1 and A2 differ by 35 CPU points. Pass 2 is higher than pass 1 for every variant (B, C, D, A), so there is a session or order drift on top of noise.

## Verdict
Hypothesis WRONG on CPU, partly right on memory.
- Avatar CPU: wrong. About 12 points (A minus C), inside the 10 to 15 percent noise. The VRM is a memory cost, not a CPU cost.
- Avatar memory: right. About 138 MB WS and about 400 MB private. This is the largest MB share the avatar takes.
- Preview: right that it is cheap. A minus B is negative (inside noise), so the preview is unproven as a cost and is not a fix target.
- Bare window: wrong on size. D is about 98 CPU points, not 25 to 40, and 314 MB WS, not 120 to 200. The bare Bevy window with a camera and light is most of the CPU. This matches the subtask 01 note that non-tracker parts use 85 to 90 points on their own.
- Prediction numbers: C saved 138 MB (predicted 200 to 300); D CPU 98 (predicted 25 to 40). The prediction falsifiers fired for D (above 50 points) and for avatar CPU (below 25 points), so the bare Bevy loop is the CPU target.
- KEEP rule: not applicable (measurement only). No code change is kept.
