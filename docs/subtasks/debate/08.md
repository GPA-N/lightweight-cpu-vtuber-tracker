# Debate 08: cap the render loop at about 30 fps

## Hypothesis
The window renders uncapped at vsync 60 fps while the avatar only changes about 15 times a second.
- Code: `window.rs:382-388` `build_app` never inserts a `WinitSettings`, so bevy_winit uses its default. `bevy_winit-0.19.1/src/lib.rs:131` `init_resource::<WinitSettings>()`, and `winit_config.rs:72-75` `Default` returns `WinitSettings::game()`: `focused_mode: Continuous` (the loop runs as fast as vsync allows, 60 fps) and `unfocused_mode: reactive_low_power(1/60 s)`.
- Measurement: every live run so far reports render FPS 60.0 (subtask 01 and 07 notes). So with focus the app does a full Bevy update, extract, prepare and present 60 times a second, most of it producing identical avatar pixels.
- Cost model: per-frame main and render-thread work (extract, prepare, queue, command encode, present, DXGI) scales with frame count. Halving frames should cut that share roughly in half.
- Counter-evidence: the previous try, `reactive_low_power(25 ms)`, gave 97 to 111 CPU against 113 (inside noise) and 40 fps. So the render-loop share may be small, or the 25 ms run was partly in unfocused mode (the earlier run did not record focus state). This is why the KEEP rule is strict.
- Cheaper explanation to watch for: the tracker runs on its own thread (ONNX, about 9 to 10 ms per frame when a face is present). With no face it idles. A render cap does not touch tracker CPU, so the cap saves only the window share (subtask 07: bare window about 98 CPU points, avatar about 12).
- Confounder: focus. The run is in the foreground, so the focused mode is the one that matters. Keep the window focused and do not touch the mouse during each run (reactive mode also wakes on window events).

## Prediction
15 s live runs, NO face, CPU average (% of one core), peak working set (MB), render FPS, and `tracker ready -> applied in renderer` median (ms). V0 expected: CPU 90 to 100, WS about 460 MB, fps 60.0, latency about 10 ms.
- V0 (baseline binary): CPU 95 (range 85 to 103), WS 460, fps 60.0, latency 9.8 to 10.5.
- V1 (`reactive(33 ms)` focused and unfocused): CPU 82 (about 14 percent below 95), WS 455 to 465, fps 30.0 to 31.0 (a value below 30.0 fails), latency +0 to +2 ms. Prediction: fails the 15 percent rule by a small margin. Falsified if both runs are at or below 81 CPU with fps at least 30 and latency rise at most 4 ms.
- V2 (`reactive_low_power(33 ms)` both modes): CPU 84 (about 12 percent below), fps 30.0 to 31.0, latency +0 to +3 ms. Predicted to fail the 15 percent rule. Falsified if CPU is at or below 81 in both runs.
- V3 (`WinitSettings::game()` plus `PresentMode::Fifo` and `desired_maximum_frame_latency: Some(1)`): CPU 93 to 97 (no change, inside noise), fps 60.0, latency -0 to -1 ms. Prediction: no KEEP. Bevy's default present mode is `AutoVsync`, which falls back to `FifoRelaxed` or `Fifo` (bevy_render window code), so the explicit Fifo should change nothing; only the frame-latency field can change anything. Falsified if CPU drops more than 15 percent with fps 60.
- Overall: I expect no variant to pass. Most likely outcome: REVERT everything.

## Verdict (project manager)

- V3: no effect (same CPU, same fps). REVERTED (the two Window lines removed).
- V1 and V2: a 30 fps cap lowers CPU by about 20 to 30 points (V1 is 16 percent below the best V0 run in both runs; V2 narrowly misses 15 percent because of one run at 74.7). Memory is unchanged. The price is a higher hand-off: about +10 ms median and +16 ms p95 (the renderer now waits up to 33 ms for a frame). Render fps is 30.3, which only just meets the 30 fps target.
- The pre-agreed KEEP rule needed the hand-off to rise by no more than 4 ms, so V1 and V2 FAIL it and are not kept. This is a real trade-off (CPU against display latency) and not a pure win: it is reported to the user as a decision, not applied.
- Prediction check: hypothesis (cap halves render CPU) was partly right: the cap saved about a quarter, not a half, because the bare window cost does not scale with frame rate alone.
