# Debate 03: Msaa::Off on the avatar camera

## Hypothesis
`crates/avatar/src/window.rs:426` spawns `Camera3d::default()` with no `Msaa` component. In Bevy 0.19 `Msaa` is a per-camera component (`bevy_render-0.19.1/src/view/mod.rs:240`) with `#[default] Sample4`, so the avatar view renders into 4x multisampled colour and depth targets and resolves them every frame. That costs GPU memory and GPU time. The CPU share is probably small (MSAA is a GPU-side resolve), so the saving should show mostly in memory, and only partly in process memory, because GPU allocations are not all counted in process private bytes. `Msaa` is in `bevy::prelude` via `bevy_render::prelude` (`bevy_render-0.19.1/src/lib.rs:74-78`), so no new import is needed.

## Prediction
- Peak working set: drop of 10 to 40 MB (2 to 9 percent of 463 MB).
- Peak private: drop of 0 to 20 MB (under 3 percent of 855 MB). Private bytes are the number the KEEP rule uses.
- CPU average: change within plus or minus 5 points (no real CPU saving expected).
- Render fps: stays at 60.
- KEEP rule: predicted to FAIL. Both AFTER runs need peak private (or CPU) more than 10 percent below both BEFORE runs. Ten percent of 855 MB is about 85 MB, which I do not expect.
- Would prove me wrong: AFTER peak private below BEFORE by more than 85 MB in both AFTER runs, or CPU average down more than 10 percent in both AFTER runs, with the BEFORE pair not overlapping.
- Measurement plan: alternate runs (before, after, before, after), no face in view, binaries copied to `target\release\live_before.exe` and `live_after.exe`.

## Result
Build: `cargo build --release -p bench -p app --bin live`, CARGO_BUILD_JOBS=4, one at a time. Binaries: `live_before.exe` built 18:44:58 (md5 a78076d8, unmodified tree). `live_after.exe` built 18:45:21 (md5 b193a20b, after `Msaa::Off` added to `window.rs:426`). Order: before, after, before, after, 15 s each, no face in view (the user was away, not verified by camera).

| run | CPU avg % | peak WS MB | peak private MB | render fps |
|---|---|---|---|---|
| s03_before_1 | 97.9 | 532.2 | 916.5 | 59.9 |
| s03_after_1 | 100.8 | 522.6 | 868.1 | 60.2 |

- Pair 2 (cleanest, matches 01 baseline): WS -8.4 MB (-1.8%), private -7.8 MB (-0.9%), CPU -5.9 points (-6.5%).
- Pair 1 is noisy: before_1 is 60 MB above the 01 baseline and after_1 sits above before_2 on private bytes.
- Render fps 60 in all runs. `median tracking latency` 0.0 ms (no face).
- Screenshot: `AVATAR_SHOT` makes the app exit, so it was a fifth run, separate from the four measurement runs. `fixtures\private\out\s03_shot.png` shows the avatar, hair, shirt and the camera panel (left). Looks fine.

## Verdict
REVERT. KEEP rule fails: AFTER private 868.1 and 848.8 MB, BEFORE min 856.6 MB, so no AFTER run beats both BEFORE runs by more than 10 percent (about 85 MB). CPU does not pass either (after_1 is higher than before_1). The one-token edit is reverted to `commands.spawn((Camera3d::default(), camera));`.
Hypothesis: direction partly right (small memory effect), magnitude wrong. Measured WS -8 MB and private -8 MB on the clean pair, under the predicted 10 to 40 MB WS and 0 to 20 MB private range only at the low end. CPU is not a MSAA effect, as predicted. Prediction "KEEP fails" held. The memory effect is real-looking but below the 10 percent rule and inside the 10 to 15 percent run noise.
